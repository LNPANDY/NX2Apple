**v1.2.4: The experimental builder compiles almost every shader itself and uses more of the Mac for the pipeline archive, with the bundled nxbuild 0.6.5.**

## English

**Changed**
- **Faster shader step**: with the experimental builder, `nxb 0.6.5` needs less CPU time for the shader step. The standalone shader step of Super Mario Bros. Wonder took 879 s of CPU time instead of 2,222 s with `nxb 0.6.4` (#834)
- **Fewer shaders for Apple's compiler**: nxb's own front end now compiles texture pools, `reinterpret_cast` and more SIMD builtins. On Super Mario Bros. Wonder, Apple's compiler made 35 shader libraries instead of 1,079. On The Legend of Zelda: Ocarina of Time for Switch 2, the own front end compiles 14,780 of 14,796 shaders of a partial build instead of 10,276 (#834)
- **Pipeline archive by the load of the Mac**: `nxb` starts Apple's compiler runs for the pipeline archive while CPU and memory use stay below 90 %. Before, 3 runs went while the shader step ran. The runs have a lower priority, so the shader step keeps the cores it needs. On a Mac with 8 GB, one run goes at a time (#834)
- **Shader threads from the cores**: `nxb` takes the number of shader threads from the cores of the Mac. Before, it was 10 on every Mac. An M2 Max still gets 10, an M1 gets 6 (#834)
- **Extract progress for a NUP**: the extract stage shows byte progress for a Switch 2 NUP, as it does for a package (#834)

**Fixed**
- **iPhone and iPad build with the experimental builder**: the build no longer rejects nxb's own iOS shader libraries with "their stamp: none". `nxb` now stamps the iOS library too and packages the guard tables of its own build, reported by @berylium, by @thehobbit85 (#851)

**Known issues**
- **Experimental builder (`nxb build`)**: how much faster a whole build is with `nxb 0.6.5` has not been measured yet. The iOS stamp fix was checked with a synthetic shader only. The iPhone and iPad path has not been run with a real game on a device (#749, #834, #851)

**Requires**
- iOS or iPadOS 26 or later
- To build NVN games on a Mac: Xcode 27.2 and macOS 26.6 or later

## 中文

**变更**
- **更快的着色器阶段**：使用实验性构建器时，`nxb 0.6.5` 的着色器阶段占用的 CPU 时间更少。Super Mario Bros. Wonder 的独立着色器阶段用了 879 秒 CPU 时间，`nxb 0.6.4` 为 2,222 秒（#834）
- **交给 Apple 编译器的着色器更少**：nxb 的自有前端现在可以编译纹理池、`reinterpret_cast` 和更多 SIMD 内建函数。在 Super Mario Bros. Wonder 上，Apple 编译器生成的着色器库从 1,079 个减少到 35 个。在 Switch 2 版《塞尔达传说 时之笛》上，自有前端可以编译一次未完成构建中 14,796 个着色器里的 14,780 个，之前为 10,276 个（#834）
- **按 Mac 负载编译管线归档**：`nxb` 会在 CPU 和内存占用低于 90% 时启动 Apple 编译器来生成管线归档。之前在着色器阶段运行时固定为 3 个。这些编译进程的优先级较低，着色器阶段仍能获得所需的核心。在 8 GB 内存的 Mac 上一次只运行一个（#834）
- **着色器线程数取决于核心数**：`nxb` 根据 Mac 的核心数决定着色器线程数。之前所有 Mac 都是 10。M2 Max 仍为 10，M1 为 6（#834）
- **NUP 的解包进度**：解包阶段对 Switch 2 NUP 也显示字节进度，和游戏包一样（#834）

**修复**
- **使用实验性构建器为 iPhone 和 iPad 构建**：不再以「their stamp: none」拒绝 nxb 自己生成的 iOS 着色器库。`nxb` 现在也为 iOS 库写入标记，并打包自己这次构建生成的守卫表，由 @berylium 报告，作者 @thehobbit85（#851）

**已知问题**
- **实验性构建器（`nxb build`）**：尚未测量 `nxb 0.6.5` 让完整构建快了多少。iOS 标记修复只用模拟着色器检查过。iPhone 和 iPad 路径尚未在真机上用真实游戏运行过（#749、#834、#851）

**系统要求**
- iOS 或 iPadOS 26 或更高版本
- 在 Mac 上构建 NVN 游戏：Xcode 27.2 和 macOS 26.6 或更高版本
